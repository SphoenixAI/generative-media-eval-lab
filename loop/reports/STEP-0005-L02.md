### Acceptance criteria copied verbatim from loop/backlog.toml

- Every derivation case is tested.
- A revision cannot borrow an earlier revision's seal.
- A revision without a reason is rejected.
- No edit can raise a record's provenance.

Sharper criteria, retaining all four backlog criteria:

- V2 contains `use_context` with `surface`, `audience` and `viewing_profile` (`FEED` or `STUDIO`); `criteria[]` with `id`, `dimension`, `priority` (`MUST`, `SHOULD`, `COULD` or `WONT`), `acceptance`, `rejection` and `tolerance`; and `expected_deviations[]` with `dimension`, `description` and `criterion_id`. Required text rejects blank or whitespace-only input. Tolerance is human-authored text, not an inferred numeric threshold. Criteria are nonempty with unique IDs; expected deviations reference an existing criterion of the same dimension within that revision. Multiple criteria may address one dimension. No dimension is labeled `SENSITIVE` or `INVARIANT`.
- Every new v2 revision, including revision 1, requires `revision_reason` equal to `SERENDIPITY`, `CLARIFICATION`, `CORRECTION` or `SCOPE_CHANGE`. A successor pins the immediate predecessor's exact reference and digest. Missing, skipped, stale, wrong-kind, cross-ID or digest-mismatched predecessor links fail admission. Constructor, serialized-input and direct-repository paths enforce the same rules, including copied nested values.
- Derive `SEALED` only when the exact intent revision's seal time is strictly before the time of the plan bound to this registration, that plan lists the exact revision, and its plan time is strictly before this clip's original registration time. Otherwise derive `CONTEMPORANEOUS` only when that exact revision was sealed strictly before this clip's first logged view. Otherwise derive `RECONSTRUCTED`, including never-sealed revisions. Equal times do not satisfy a strict ordering. A missing first-view event cannot establish contemporaneity, but does not negate an independently satisfied sealed ordering.
- Seal evidence pins the exact intent revision and digest. Another revision's seal does not qualify the current revision. A plan for another revision or registration does not establish the sealed ordering. Missing or nonqualifying chronological evidence degrades to the supported class; malformed times, invalid reference kinds, inconsistent registration anchors and digest tampering are rejected. Missing event times remain absent; derivation never substitutes the current clock or an edit timestamp.
- Chronological provenance is computed, never selected by the author. The sole declaration is `PROMPT_ONLY`, permitted only for `FOUND` clips. A found clip without that declaration follows the ordinary rules, without borrowing an unrelated plan. Constructors, copied objects, serialized input and direct writes cannot supply a stronger label.
- A binding retains immutable registration anchors, exact intent and predecessor pins, and the evidence needed to replay its result. Successors may preserve or lower provenance, never raise it. Changing timestamps, adding seal evidence, changing intent revision, renaming a binding, or cloning both media and ingestion IDs cannot reset the historical ceiling. Check this inside repository write admission, including competing writers. Exact replay remains idempotent; rejected writes leave historical payloads unchanged.
- Use one shared content-identity rule for admission and snapshot membership: validated source checksum equality groups byte-identical registration aliases into one binding lineage. Each binding also pins its original registration/media evidence; successors cannot change those anchors. This deliberately conservative local policy does not claim that identical content proves a common generation event. Renamed anchors cannot create a second lineage; genuinely different content can have an independent lineage. The same rule must work when an alias receives the first binding, with no earlier binding on the selected clip's exact references.
- `PilotWorkspace.snapshot` and `export_snapshot` include every relevant binding revision and the transitive closure of its pinned dependencies for selected clips, including the alias-first case. Unrelated content is excluded. A later revision cannot change an earlier snapshot/export; repository reopening preserves the same bytes and pins. Exercise the actual workspace path with generated TEST-ONLY media, rather than a mocked traversal.
- Pilot 0 intents load through an explicit read-only compatibility view as `RECONSTRUCTED`. Their original references, canonical payloads and digests remain unchanged. The view invents no revision reason, criteria, context, seal or plan. A legacy binding cannot acquire stronger provenance through loading or a v2 adaptation. The existing v1 authoring API remains a documented legacy path; all newly authored v2 records require the new contract.
- Document what each class records and what it cannot prove. `SEALED` records the specified local ordering; `CONTEMPORANEOUS` records sealing before the first logged view when the sealed predicate fails; `RECONSTRUCTED` records insufficient qualifying chronology; `PROMPT_ONLY` records a permitted declaration for found content. None is a quality verdict or proof of generation order. Explain I7's restrictions without implementing acceptability: reconstructed and prompt-only intent cannot excuse a material deviation; contemporaneous intent requires a flag. Missing judgment evidence stays `UNKNOWN`.

### Method claims and checkable local contracts

External claims are individually identified for deterministic extraction. Primary sources were opened during planning on 2026-10-08; the later research phase remains independent.

CLAIM L02-P5-M01: Pydantic v2 BaseModel.model_copy(update=...) does not validate the supplied update values before creating the copied model.

Source: [Pydantic v2 model_copy documentation](https://docs.pydantic.dev/2.12/api/base_model/#pydantic.main.BaseModel.model_copy). Consequence: preserve serialized revalidation at admission and test invalid nested copied values; frozen assignment alone is insufficient.

CLAIM L02-P5-M02: SQLite permits only one simultaneous write transaction, and BEGIN IMMEDIATE starts a write transaction immediately or can fail with SQLITE_BUSY when another connection already has an active write transaction.

Source: [SQLite transaction documentation, sections 2.1 and 2.2](https://www.sqlite.org/lang_transaction.html). Consequence: check mutable binding history on the same connection after the existing immediate transaction begins, and test competing admissions using separate connections to a temporary file-backed database. This makes no claim about another database backend.

CLAIM L02-P5-M03: RFC 3161 describes time-stamping evidence that a datum existed before a particular time.

Source: [RFC 3161, introduction](https://www.rfc-editor.org/info/rfc3161/). This bounds the documentation's explanation of timestamp evidence; no timestamp-service implementation or standards-conformance claim is proposed.

CLAIM L02-P5-M04: Local seal, plan, registration and first-view timestamps alone cannot prove that a clip was generated after its intent was sealed.

This is an inference, required as a limitation by L02. Counterexample: a previously generated clip can be registered and first logged as viewed after a new seal and plan. Even witnessing intent existence does not itself witness clip generation, consistent with [RFC 3161's proof-of-existence scope](https://www.rfc-editor.org/info/rfc3161/).
