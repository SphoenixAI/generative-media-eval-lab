## Plan

### Goal and relevance to NORTH_STAR.md

Implement L11, Relation v2, as an additive domain and repository contract for human-authored relations. Store criterion anchors, separate epistemic and operational purposes, and the author's warrant, qualifier and rebuttal without inferring a judgment. Provide an explicit read-only compatibility loader for legacy relations.

This supports the evidence-linked and actionable evaluation thesis in `loop/NORTH_STAR.md`: a reviewer can inspect what an edge claims, which exact intent criteria it concerns, and why its author asserts it. It supplies relation infrastructure for the flagship case; it does not demonstrate that a case is resolved, that an argument is sound, or that the intent study has run.

This is P2 planning only. This call changes only this report's Plan section. Implementation, probes and tests belong to the later build call; plan sealing, authoritative gates and integration belong to the controller.

Sharper criteria implementing the item's notes, without replacing the criterion above:

1. Add a separately registered `RelationClaimV2` with `schema_version=2`. Retain the existing relation information: subject, predicate, object, epistemic status, evidence references, author, free-text purpose, scope, validity interval and optional claim confidence. Add `creative_anchor`, `epistemic_purpose`, `operational_purpose`, `warrant`, `qualifier` and `rebuttal`. Retain all eight current predicates: `supports`, `contradicts`, `motivated_by`, `fulfills`, `violates`, `alternative_to`, `compatible_with` and `refines`. Do not change the serialized fields or digest contract of `RelationClaim` or other v1 records.
2. A newly authored v2 relation must explicitly supply `epistemic_purpose` from `SUPPORT`, `RULE_OUT`, `DISCRIMINATE`, `LOCALIZE`, `EXPLAIN`, `QUALIFY`, `SCOPE`, `OPERATIONALIZE`, and `operational_purpose` from `SHIP`, `REPAIR`, `REGENERATE`, `REVISE_RUBRIC`, `ADD_GOLD`, `RETRAIN_SIGNAL`, `INVESTIGATE`. Reject omitted, null, blank, wrong-case and unknown values, including `UNSPECIFIED` on this new-authoring path. The two vocabularies are independent declarations: no predicate-to-purpose inference, action execution or required pairing is introduced.
3. The v2 `intent` is a `Pin` containing an exact `IntentSpecV2` or legacy `IntentSpec` reference and digest. `creative_anchor` is a tuple of distinct, nonblank criterion IDs, with an empty tuple meaning that no criterion anchor was supplied. Every supplied ID must exist in that exact stored `IntentSpecV2` revision. An ID present only in a newer revision, another intent or a different digest fails admission. A legacy intent has no criterion IDs and therefore permits only an empty anchor; never manufacture IDs from dimensions, positions or text. Anchors are linkage metadata, not an assessment or an excuse for a deviation.
4. `supports` and `contradicts` require a human-supplied, nonblank `warrant`. Missing, null, empty and whitespace-only warrants fail for both predicates. Other predicates may omit the warrant. `qualifier` and `rebuttal` are optional human-authored text: absent values remain `None`; supplied values must be nonblank and survive serialization unchanged. Retain the old free-text `purpose` separately; it is neither a default warrant nor a source from which the new purposes are inferred.
5. Preserve relation endpoint, evidence-kind, timezone and validity-interval checks. Preserve the prohibition on an `observed` status for hypothesis claims and the self-relation checks for `compatible_with` and `refines`. Intent endpoints must equal the relation's exact intent reference. A hypothesis endpoint must have that same reference as its own intent; matching IDs across revisions or intent versions is insufficient. Existing hypotheses currently require legacy intent, so v2 relations involving those hypotheses must pin that legacy intent and have empty anchors. Criterion-anchored v2 `fulfills` and `violates` edges can target `IntentSpecV2` directly. Do not silently reinterpret an existing hypothesis under a v2 intent or expand hypothesis authoring in this item.
6. Repository admission validates every reference and every pin, including input copied or deserialized outside the usual constructor path. Evidence, including an evidence subject omitted from the separate evidence list, must be scoped to the declared intent. For legacy intent, retain the existing media-to-intent checks. For v2 intent, require a retained `IntentBinding` with the same media reference and exact intent pin; do not infer a binding from coincident criterion names, choose the latest intent, or create a binding during relation admission. Missing or mismatched references fail admission with an actionable error and no relation write. Bindings and their provenance remain unchanged.
7. V2 revisions are append-only. Revision 1 has no predecessor; every successor pins the immediately previous revision of the same relation kind and ID, including its digest. Missing, skipped, wrong-kind, wrong-ID and digest-mismatched predecessor pins fail. Exact replay is idempotent; a conflicting payload at an existing revision is rejected. Reopening the repository and appending a new revision leave earlier canonical payloads and hashes unchanged.
8. V2 `compatible_with` relations must participate in the existing exclusive-competing-set constraint. Reject a compatible pair in either endpoint order when a retained exclusive set contains the exact hypothesis references, and reject admission of such a set after either a v1 or v2 compatible relation. Retain the existing transaction admission boundary and historical-set semantics. Do not permit the new artifact kind to bypass L07 through direct repository writes, copied objects or competing writers.
9. Add `load_relation(repo, ref)` as the common explicit read entry point for v1 and v2 relations. For v1 it returns a read-only `LegacyRelationView` preserving the source reference, canonical payload and digest, exposing both new purposes as `UNSPECIFIED`, empty anchors, and absent warrant, qualifier and rebuttal. The source's original free-text purpose and other authored values remain accessible. The view is not a registered artifact and cannot be persisted as an automatic migration. Loading creates no new records and never synthesizes a warrant for a legacy support or contradiction. Existing `Repository.get` and the v1 CLI continue to return/use their original v1 records; document the compatibility loader explicitly rather than claiming an implicit database migration.
10. Verify structural behavior with new TEST-ONLY tests: all purpose values and predicates, valid and invalid anchors and pins, warrant boundaries, optional-text round trips, exact revision links, legacy loading, stored-byte preservation, repository reopening, exclusive-set conflicts in both insertion orders, and negative cases through direct admission. Fixed timestamps and literal expected field values are the oracles; demonstrate stable canonical output and hashes for repeated parsing/replay of the same complete input. Give each rejection probe a fresh identity so an unrelated immutable-revision conflict cannot make it pass. Include unchanged public/embed payload checks with private sentinel relation text and unchanged hypothesis status/confidence after relation storage.

### Invariants at risk

- **I1:** Relation text, anchors and purposes are human judgments for real clips. The build accepts supplied values only; the loop uses TEST-ONLY synthetic records and temporary roots, never writes `pilot-local/`, and never supplies real judgments.
- **I2:** Legacy omissions and absent warrants could be mistaken for evidence or success. Keep compatibility purposes `UNSPECIFIED`, optional text/confidence absent, and quality verdicts unchanged; an empty anchor is not a passed criterion. Validation failure is not an evaluation verdict.
- **I3:** New fields or migration could alter old hashes or overwrite revisions. Preserve v1 source bytes and use exact predecessor pins and append-only v2 admission; test replay, rejection and reopening.
- **I4 and I16:** An additive type could prompt regeneration of accepted artifacts or modification of the judge. Change no protected files, schemas, harness code, prompts, rubric, invariants, baseline or north star. Do not regenerate outputs to accommodate new records.
- **I5 and I7:** Creative anchors could be treated as measurements or automatically excuse deviations. They only reference criteria in a pinned intent; this step creates no technical-observation type, acceptability assessment or intent-provenance promotion, and implements no deviation exception.
- **I6, I8 and I9:** Operational-purpose labels or relation support could mutate evaluations, resolve hypotheses, average failures or combine confidence. Store the labels and individual optional confidence only; compute no decision, aggregate, probability or information gain.
- **I10 and I11:** Use existing dependencies and offline runtime paths. Add tests in a new file; do not edit, remove, rename, skip, xfail, deselect or loosen existing tests.
- **I12:** Warrants, qualifiers and rebuttals may contain private notes. Keep the new records in the private domain/repository path and prove public/embed outputs remain sanitized.
- **I13:** Limit determinism claims to replay of complete fixed inputs, test them, and record actual tool versions, source hashes and verification results during building. Generated event timestamps are not deterministic outputs.
- **I14 and I15:** Stay within L11 and the 900-line gate. Purpose enum members are labels only; they do not authorize deferred capabilities. No main changes, push, merge or force-push is part of this call.
