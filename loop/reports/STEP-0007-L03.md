## Plan

### Goal and relevance to NORTH_STAR.md

Implement L03, Seal and verify: give a human-authored intent file a reproducible content digest, retain its immutable local seal, and provide explicit verification through `eval-pilot seal-intent FILE` and `eval-pilot verify-seal ID|FILE`. This supplies the sealed-intent stage of the flagship case in `loop/NORTH_STAR.md` and supports the lab's evidence-linked, reproducible evaluation thesis. It establishes a local integrity mechanism, not a completed human case, acceptable media, or proof of generation chronology.

This call is P2 planning only. Only this report's Plan section changes. Implementation, tests and probes belong to the subsequent build call; plan sealing, authoritative gates and integration belong to the controller. No code, human records, test results or seals are created in this call.

### Acceptance criteria copied verbatim from loop/backlog.toml

- The digest is stable across key order and whitespace.
- Any change to a value changes the digest.
- Key-ordering vectors with non-ASCII keys pass.
- Tampering is detected.
- Seals are immutable.

Sharper criteria and explicit boundaries, retaining all five criteria:

1. Canonicalization follows claims M01-M05 below for the supported JSON subset. Independently specified canonical bytes and SHA-256 expectations cover nested objects, objects inside arrays, empty containers, strings, integers, booleans and null. Key permutations, insignificant whitespace and equivalent string escapes produce the same digest; array reordering and each distinct value mutation in the test corpus produce a different digest. String whitespace remains content. The verbatim value-change criterion is tested over explicit mutations, not represented as a mathematical collision-free guarantee; M08 explains that limit.
2. The integer-only input profile accepts integer JSON tokens within `[-9007199254740991, 9007199254740991]`. It rejects fractional and exponent tokens, including `1.0` and `1e0`, instead of rounding or coercing them, and rejects larger integers rather than silently losing information. This is an explicitly narrower application profile, not a claim that RFC 8785 forbids other numbers. Errors identify the unsupported value and advise using an integer literal for an exact in-range integer, otherwise a human-authored textual representation in a schema-permitted text field or a separately approved numeric extension. No automatic conversion to strings or editing of the input occurs. Include negative-zero and range-boundary cases.
3. Strict input handling rejects duplicate decoded keys, malformed JSON, invalid Unicode, non-finite numeric constants and unsupported types before a seal is written. The RFC non-ASCII ordering vector is an independent oracle, including a supplementary-plane key whose order differs from code-point sorting. Mark surrounding fixtures TEST-ONLY while preserving the published vector's original ordering data.
4. `seal-intent FILE` accepts a complete human-authored `IntentSpecV2` JSON artifact, with explicit `id`, `schema_version`, `revision` and timezone-bearing `created_at`, and validates the existing L02 contract. It reads one source buffer, validates and hashes that same buffer's parsed content, and never rewrites the file or invents objective, criteria, owner or revision reason. The file digest covers the whole supplied JSON document before model defaults or datetime serialization can change its representation. Legacy v1 forms remain on their existing path and receive a useful error if supplied to this command.
5. An append-only `SealRecord` records the content digest, canonicalization method and integer-profile identifier, UTC `sealed_at`, actual tool version, resolved source path, and nullable `git_witness` containing commit and remote URL. It also retains the canonical source text privately and pins the exact `IntentSpecV2` reference and existing artifact digest. These two digests have different named purposes: the new JCS file digest must never replace `Artifact.digest`, predecessor pins or accepted hashes. Optional witness fields are supplied together as explicitly declared metadata; no remote lookup or authenticated-witness claim is made. The command assigns the seal time and seal ID; it accepts no backdating option.
6. Sealing may import the validated, human-supplied intent revision into the existing repository, then append its seal. An identical existing revision is reusable; different content under the same revision, missing predecessors and incorrect predecessor pins fail. Each seal is a single immutable event with revision fixed to 1; repeated sealing may append a distinct event but cannot replace the earlier event or its time. Repository replay of an identical seal is idempotent. If seal admission fails after an intent was imported, report the failure explicitly and retain that append-only intent for retry; do not claim a seal exists or delete the imported record. This plan does not introduce a general multi-artifact transaction API.
7. `verify-seal ID` addresses an exact seal ID and checks its stored integrity, canonical source, pinned intent and current source-file digest. `verify-seal FILE` means the original intent source file, not an untrusted standalone seal certificate: resolve the path and check every retained seal recorded for that path. Do not select only the newest matching seal or match solely by the current content digest, which could conceal a changed file. Report results by seal ID. Unknown IDs, unsealed paths, absent databases and unavailable sources yield explicit UNKNOWN with a nonzero exit status; detected corruption, invalid content or digest mismatches yield an explicit integrity failure with a nonzero exit status. Success requires all requested checks to succeed. Integrity status never supplies a quality verdict.
8. Verification is read-only, including when the workspace does not exist: it must not initialize a database, create directories, reseal, repair records or change timestamps. Wire its CLI dispatch before the current write-initializing `PilotWorkspace` path. A moved or missing original source does not receive a successful source check merely because archived canonical text remains available.
9. Immutability covers frozen model values, copied/serialized inputs at repository admission, rejection of seal revision 2, same-ID conflicts, and the existing database UPDATE/DELETE prohibition. Check the canonical text, claimed file digest and intent pin together at admission and verification. Historical bytes remain unchanged after reopening, rejected writes and repeated sealing. A later intent revision cannot borrow another revision's seal. No new sealing command changes an existing `IntentBinding` or raises its provenance.
10. All execution fixtures use explicit TEST-ONLY text and temporary roots outside `pilot-local/`. No real clips are needed. Existing tests and accepted artifacts remain unchanged. No dependency is added. Canonicalization is deterministic and tested across separate processes; seal IDs and wall-clock event times are event metadata and are not claimed deterministic. Private canonical text, paths and witness metadata never enter public/embed serializers.

### Method claims and their verification sources

Each external method claim appears on its own CLAIM line for deterministic extraction. Sources were inspected during planning on 2026-10-09; independent research remains a later loop phase. Numeric limits and CLI behavior proposed above are application contracts, except for the external numeric fact identified in M06.

CLAIM L03-P7-M01: RFC 8785 requires recursive object-key sorting by unsigned UTF-16 code units while preserving array order.

CLAIM L03-P7-M02: RFC 8785 emits no insignificant whitespace and encodes canonical output as UTF-8.

CLAIM L03-P7-M03: RFC 8785 preserves Unicode string data without normalization and rejects duplicate object names and lone surrogates.

CLAIM L03-P7-M04: RFC 8785 uses short escapes for backspace, tab, newline, form feed and carriage return, lowercase hexadecimal escapes for other ASCII controls, and escapes quotation marks and backslashes.

CLAIM L03-P7-M05: RFC 8785 bases number serialization on ECMAScript binary64 behavior, rejects NaN and Infinity, and serializes negative zero as zero.

Sources for M01-M05: [RFC 8785, sections 3.1-3.2.4 and Appendix B](https://www.rfc-editor.org/rfc/rfc8785). Use the section 3.2.3 vector verbatim as test data. These claims govern the canonicalizer; passing only ASCII sorting cases is insufficient.

CLAIM L03-P7-M06: RFC 7493 states that a receiver cannot be expected to treat integers outside the inclusive range [-9007199254740991, 9007199254740991] as exact values.

Source: [RFC 7493, section 2.2](https://www.rfc-editor.org/rfc/rfc7493#section-2.2). Choosing this range for L03 is a conservative application decision; it avoids expanding the approved integer-only work into general floating-point serialization.

CLAIM L03-P7-M07: SHA-256 as specified in FIPS 180-4 produces a 256-bit message digest.

CLAIM L03-P7-M08: A fixed 256-bit digest cannot be injective over more than 2^256 distinct messages, so SHA-256 cannot guarantee a different digest for every possible value change.

Source for M07: [FIPS 180-4, sections 1 and 6.2](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.180-4.pdf). M08 is a mathematical inference by counting possible outputs, not an empirical collision claim. Keep the backlog wording intact and report the tested mutation coverage honestly.

CLAIM L03-P7-M09: Python 3.12's standard library provides hashlib.sha256 for hashing bytes and hexdigest for hexadecimal digest output.

Source: [Python hashlib documentation](https://docs.python.org/3.12/library/hashlib.html). No cryptographic implementation or third-party hashing dependency is required.

CLAIM L03-P7-M10: Python's json decoder accepts repeated object names and non-finite constants by default, and provides object_pairs_hook, parse_float and parse_constant hooks for stricter decoding.

Source: [Python json documentation](https://docs.python.org/3.12/library/json.html). Strictness must be explicit and tested before information is discarded by default parsing.

CLAIM L03-P7-M11: Pydantic v2 model_copy(update=...) does not validate update values before creating the copied model.

Source: [Pydantic model_copy documentation](https://docs.pydantic.dev/2.12/api/base_model/#pydantic.main.BaseModel.model_copy). Preserve repository revalidation and test copied seal fields; frozen assignment alone is insufficient.

CLAIM L03-P7-M12: SQLite allows only one simultaneous write transaction, and BEGIN IMMEDIATE starts one immediately or can fail when another connection already holds a write transaction.

Source: [SQLite transactions, sections 2.1-2.2](https://www.sqlite.org/lang_transaction.html). Reuse the existing transaction boundary for seal-pin admission checks; make no claim about other database backends.

CLAIM L03-P7-M13: SQLite's URI mode=ro opens a database for read-only access and does not create a missing database.

Source: [SQLite URI filenames, mode query parameter](https://www.sqlite.org/uri.html). Verification must also avoid application-level workspace initialization.

CLAIM L03-P7-M14: A local content digest, local clock reading and declared Git commit/remote pair do not independently prove authorship, generation order or externally witnessed existence at the recorded time.

M14 is an explicit threat-model inference: an operator can supply a pre-existing clip after sealing, alter a local clock, or declare a commit/remote pair without an external verification event. Likewise, a database administrator who replaces both records and their stored hashes is outside the local integrity guarantee. These counterexamples are checkable without calling a timestamping or Git service. No external timestamping, signature, identity or remote-attestation mechanism is proposed.
